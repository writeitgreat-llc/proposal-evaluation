# proposal-evaluation -- parameterised routes that are intentionally reachable
# without a login, because the URL itself is the credential.
#
# Format:  <url rule>   # why it is safe
#
# Adding a line here is a security decision. Before you add one, answer:
#   1. Is the parameter unguessable? (>= 128 bits of randomness, not sequential)
#   2. Is the data behind it disclosable to anyone holding the link?
#   3. Does the link expire?
# If the answer to any of those is no, add a guard instead of an entry here.

# --- password reset: uuid4 hex (122 bits), single use, 1 hour expiry ---
# Author.generate_reset_token / AdminUser / Publisher all use uuid.uuid4().hex
# and set password_reset_expires = utcnow() + 1h; verify_reset_token() rejects
# expired tokens and the handler clears the token after a successful reset.
/author/reset-password/<token>       # uuid4 reset token, 1h expiry, cleared on use
/publisher/reset-password/<token>    # uuid4 reset token, 1h expiry, cleared on use
/admin/reset-password/<token>        # uuid4 reset token, 1h expiry, cleared on use

# --- evaluation results: capability URL mailed to the author ---
# FIXED 2026-07-21 (security/results-tokens). The old note here warned that
# generate_submission_id() ("WIG-<YYYYMMDD>-<5 hex>", ~20 bits behind a
# guessable date) was the only key to these pages. Now every NEW proposal gets
# results_token = secrets.token_urlsafe(16) (128 bits) and these routes resolve
# through _resolve_proposal_results_key(): token first, and a token-bearing row
# addressed by its short submission_id 404s. check_route_guards.py therefore
# classifies them GUARDED (resolver helper), so these entries are dormant.
# They stay listed deliberately: LEGACY rows (results_token IS NULL, created
# before the migration -- there is intentionally no backfill) are still served
# by their low-entropy submission_id so links already emailed to authors keep
# working. That residual surface shrinks to zero as old rows age out; if it
# ever needs to be closed early, backfill tokens and re-send the links --
# do NOT add new low-entropy keys on this pattern.
/results/<submission_id>             # token-first; submission_id honoured only for legacy token-less rows
/download/<submission_id>            # PDF of the same report, same rule
/api/status/<submission_id>          # same rule; leaks only a status string

# --- analytics collector: deliberately public, no parameter at all ---
# Added 2026-07-29 with the first-party analytics collector
# (analytics_collect.py). Both routes are unauthenticated ON PURPOSE: they are
# called by anonymous visitors on the public funnel pages, before an account
# exists, which is the entire point of them.
#
# Against the three questions at the top of this file: neither route takes a
# URL parameter, so there is nothing to guess or enumerate, and neither one
# READS anything. /e appends to a write-only outbox; /consent sets a cookie
# recording the caller's own preference. The worst a hostile client achieves is
# inflating its own visit counts or flipping its own analytics choice, and
# every identity field on a stored event (visitor_hash, session_id, country,
# browser, os, is_bot, the timestamp) is derived server-side and ignores
# anything the client claims. Hardened like /api/submit: a size cap checked
# before the body is parsed, a per-IP sliding window, no IP or User-Agent
# written anywhere, and 204 for every outcome a visitor can cause.
#
# NOTE these two lines are documentation, not enforcement. check_route_guards.py
# is invoked with --app app.py and only inspects rules containing <...>, so it
# never sees either of these; they are listed here because this file is where
# somebody auditing "what in this app is reachable without a login" will look.
/e                                   # analytics beacon: no parameter, write-only outbox, no client-controlled identity
/consent                             # records the caller's own cookie choice; sets only their own cookie

# --- liveness probe: deliberately public, no parameter at all ---
# Added 2026-08-03 with the error-tracking + uptime work. An external monitor
# has to be able to call this without credentials, which is the whole point of
# it: a check that needs a login only proves the login works.
#
# Against the three questions at the top of this file: no URL parameter, so
# nothing to guess or enumerate, and it READS nothing belonging to anybody. The
# response is four fields — ok, db, release, time — none of which is a
# secret. `release` is the Heroku release number, which is already visible in
# every deploy log and identifies a build, not a person.
#
# The one real disclosure decision here is what a FAILURE says, and the answer
# is deliberately "error" and nothing else: an unredacted SQLAlchemy connection
# error renders the DSN, so the exception text goes to Sentry and the log and
# never into the body. If anyone ever adds detail to that response, this line
# stops being true.
#
# NOTE, same as the two lines above: this is documentation, not enforcement.
# check_route_guards.py only inspects rules containing <...>, so it never sees
# this route; it is listed because this file is where somebody auditing "what
# in this app is reachable without a login" will look.
/healthz                             # liveness probe: no parameter, reads nothing, never echoes the exception
